Guida operativa

Come caricare le evidenze nel repository privato

Questa pagina spiega, in ordine rigoroso, come preparare file, naming, branch, commit e pull request nel repository privato. L’obiettivo è evitare caos, duplicazioni, path errati e perdita di tracciabilità tra modulo eseguito ed evidenze caricate.

Prima di iniziare

Ogni partecipante lavora solo nella propria area dedicata evidence/participants/participant-N/ e carica esclusivamente materiale relativo al modulo in corso. Le cartelle consolidate e di governance restano di competenza del maintainer.

Prima di creare file nel repository privato, verifica sempre tre cose: numero modulo corretto, identità del partecipante coerente con il path e descrizione sintetica dell’evidenza. Se uno di questi tre elementi è ambiguo, rinomina il file prima del commit.

⚠ Regola fondamentale

Non lavorare mai direttamente su main. Usa sempre un branch dedicato nel formato participant-N/module-XX e apri una pull request verso main solo quando il set è coerente e completo. Solo il maintainer può fare merge.

Struttura di destinazione

Le evidenze individuali vanno in evidence/participants/participant-N/module-XX/. Le sottocartelle screenshots/, cli-and-configs/, pcaps/ e tests-and-notes/ sono predisposte per ogni partecipante al momento della pubblicazione di ciascun modulo.

Naming obbligatorio dei file

Il naming di device, VLAN, evidenze, cartelle e branch è congelato per tutto il percorso ed è mantenuto in un’unica fonte, per evitare copie che possano disallinearsi nel tempo.

ⓘ Fonte unica del naming

Consulta knowledge-base/meta/naming-conventions.md nel repository privato per il pattern completo (module-XX__participant-N__scope__artifact-type__short-description__vNN.ext), il naming dei device, le VLAN congelate e il naming dei branch. Il link è consultabile solo dai collaboratori autenticati sul repository privato.

Flusso operativo consigliato

Segui questi passi in ordine. Non saltare la verifica del branch prima di toccare i file e non aprire la PR finché il set non è completo.

  1. Crea il branch: git checkout -b participant-N/module-XX
  2. Verifica di essere sul branch corretto prima di copiare qualsiasi file.
  3. Copia le evidenze locali nelle cartelle corrette del repository.
  4. Controlla naming, estensioni e path finali.
  5. Apri ogni file critico per assicurarti che non sia corrotto o vuoto.
  6. Fai commit con messaggio leggibile:
    module-XX: add participant-N evidence set v01
  7. Apri la pull request verso main solo quando il set è coerente e completo.

Checklist pre-pull request

  • Il branch è participant-N/module-XX e non contiene materiale di altri moduli.
  • Le evidenze sono tutte nella cartella del modulo corretto.
  • I nomi dei file seguono il pattern congelato.
  • Non ci sono duplicati inutili o file temporanei.
  • Gli screenshot si aprono correttamente.
  • I file .txt o .md sono leggibili e completi.
  • Le running-config condivise sono in gns3/configs/module-XX/.
  • L’export GNS3 condiviso è in gns3/exports/module-XX/.
  • La checklist del modulo in docs/verification/module-XX-checklist.md è compilata e committata.
  • La PR descrive cosa è stato caricato e cosa è ancora mancante.

Errori da evitare

Non caricare evidenze direttamente su main. Non usare nomi generici come test.png, screen finale.png o config nuovo.txt. Non mischiare moduli diversi nello stesso commit. Non salvare output importanti come screenshot di terminale sfocati se puoi esportare un file testuale leggibile.

Non caricare le running-config o gli export GNS3 nelle cartelle individuali dei partecipanti: quei file sono condivisi e vanno in gns3/configs/ e gns3/exports/. Ogni volta che un’evidenza è mal posizionata o mal nominata, la review diventa più lenta e aumenta il rischio di dover rifare il caricamento.
