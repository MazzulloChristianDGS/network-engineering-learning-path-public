Guida operativa

Come caricare correttamente le evidenze nel repository privato

Questa pagina spiega, in ordine rigoroso, come preparare file, naming, branch, commit e pull request nel repository privato. L'obiettivo è evitare caos, duplicazioni, path errati e perdita di tracciabilità tra modulo eseguito ed evidenze caricate.

Prima di iniziare

Ogni partecipante deve lavorare solo nella propria area dedicata dentro evidence/participants/person-N/ e deve caricare esclusivamente materiale relativo al modulo in corso. Nessuna evidenza grezza va salvata in cartelle consolidate o in aree di governance, che restano di competenza del maintainer.

Prima di creare file nel repository privato, verifica sempre tre cose: numero modulo corretto, identità del partecipante coerente con il path e descrizione sintetica dell'evidenza. Se uno di questi tre elementi è ambiguo, il file va rinominato prima del commit.

Struttura di destinazione

La regola base è semplice: le evidenze individuali vanno in evidence/participants/person-N/module-XX/. Eventuali sottocartelle locali come final-tests/ o notes/ possono essere usate solo se già previste nelle istruzioni del modulo e devono restare dentro la directory del modulo.

Naming corretto dei file

Ogni file deve rispettare la convenzione congelata: module-XX__person-N__scope__artifact-type__short-description__vNN.ext. Questa convenzione non è opzionale, perché serve a capire modulo, autore, contenuto e revisione del file senza doverlo aprire.

  • module-00__person-1__host__screenshot__gns3-installed__v01.png
  • module-00__person-2__gns3__cli-output__setup-wizard-summary__v01.txt
  • module-00__person-3__iosv__screenshot__template-ready__v02.png

Il numero di versione aumenta solo quando il file viene corretto o sostituito. Non usare nomi vaghi come test1.png, screen finale.png o config nuovo.txt.

Flusso operativo consigliato

  1. Crea o aggiorna un branch dedicato coerente con il modulo, ad esempio participant-1/module-00.
  2. Verifica di essere sul branch corretto prima di toccare i file.
  3. Copia le evidenze locali nella directory giusta del repository.
  4. Controlla naming, estensioni e path finali.
  5. Apri ogni file critico almeno una volta per assicurarti che non sia corrotto o vuoto.
  6. Fai commit con messaggio leggibile, ad esempio module-00: add participant-1 evidence set v01.
  7. Apri una pull request verso main solo quando il set è coerente e completo.

Checklist di controllo prima della pull request

  • Il branch è quello giusto e non contiene materiale di altri moduli.
  • Le evidenze sono tutte nella cartella del modulo corretto.
  • I nomi dei file seguono il pattern congelato.
  • Non ci sono duplicati inutili o file temporanei.
  • Gli screenshot si aprono correttamente.
  • I file .txt o .md sono leggibili e completi.
  • La PR descrive cosa è stato caricato e cosa è ancora mancante.

Errori da evitare

Non caricare evidenze direttamente su main, non usare nomi generici, non mischiare moduli diversi nello stesso commit e non salvare output importanti come screenshot di terminale sfocati se puoi esportare un file testuale leggibile. Ogni volta che un'evidenza è poco leggibile o mal posizionata, la review diventa più lenta e aumenta il rischio di dover rifare il caricamento.
