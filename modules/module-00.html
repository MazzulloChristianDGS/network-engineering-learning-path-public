Modulo 00

Setup ambiente GNS3

Prima di avvicinarsi a qualsiasi protocollo di rete è necessario disporre di un ambiente di laboratorio funzionante, stabile e replicabile. Questo modulo guida l’installazione completa di GNS3, la configurazione delle immagini Cisco IOS/IOSvL2 e la verifica che l’ambiente sia pronto a supportare tutti i moduli successivi.

Obiettivo del modulo

Al termine di questo modulo il partecipante sarà in grado di svolgere autonomamente le seguenti attività:

  1. Installare GNS3 su un sistema Windows, macOS o Linux, verificarne il corretto avvio e configurare GNS3 VM come hypervisor di backend.
  2. Importare le immagini Cisco IOSv (router) e IOSvL2 (switch) in GNS3, verificarne la firma e associarle ai template corretti.
  3. Creare un progetto GNS3 vuoto seguendo le convenzioni di naming del percorso, posizionare i device sulla canvas e avviarli senza errori.
  4. Verificare la connettività tra due device usando un cloud o uno switch di management, e salvare una prima topologia come snapshot di riferimento.
  5. Configurare Wireshark come sniffer integrato in GNS3 e catturare il traffico su un link attivo, salvando la capture nella cartella prevista dal repo privato.

Stato del laboratorio all’ingresso

Il laboratorio è completamente vuoto. Non esiste ancora nessun progetto GNS3, nessun device configurato, nessuna topologia. Questo modulo è il bootstrap assoluto: l’unico prerequisito è disporre di un sistema host con almeno 16 GB di RAM, un processore con virtualizzazione hardware abilitata (Intel VT-x o AMD-V) e 50 GB di spazio disco libero.

⚠ Requisiti minimi hardware

RAM: 16 GB (consigliati 32 GB). CPU: 4 core fisici con VT-x/AMD-V abilitato nel BIOS. Disco: 50 GB liberi per immagini, progetti e capture.

Teoria

Cos’è GNS3 e come funziona

GNS3 (Graphical Network Simulator 3) è un emulatore di rete open source che permette di eseguire immagini reali di sistemi operativi di rete — Cisco IOS, IOSv, IOSvL2, FRR, VyOS e molti altri — all’interno di macchine virtuali o processi containerizzati sul tuo sistema host. A differenza di un simulatore (che riproduce il comportamento teorico di un protocollo), GNS3 esegue il binario originale del sistema operativo: i pacchetti che circolano nel laboratorio sono pacchetti reali, le tabelle di routing sono tabelle reali, e gli errori di configurazione producono gli stessi effetti che produrrebbero su hardware fisico.

GNS3 è composto da due componenti principali: il GNS3 GUI, che gira sull’host e fornisce l’interfaccia grafica per disegnare le topologie, e il GNS3 Server, che può essere locale oppure remoto (GNS3 VM). Per questo percorso è obbligatorio usare GNS3 VM come backend perché le immagini Cisco IOSv richiedono KVM/QEMU.

Immagini Cisco IOSv e IOSvL2

Cisco IOSv è l’immagine di un router Cisco virtualizzato, distribuita da Cisco per ambienti di lab. Non è una simulazione: è il sistema operativo IOS reale compilato per architettura x86. IOSvL2 è la variante per switch Layer 2, con supporto a VLAN, STP, 802.1Q trunk e tutte le feature di switching. Entrambe le immagini sono file .qcow2 che GNS3 importa come template e monta come disco della macchina virtuale ad ogni avvio del device.

ⓘ Nota legale e accesso alle immagini

Le immagini Cisco IOSv sono distribuite sotto licenza e richiedono un account Cisco con accesso a Cisco DevNet oppure a Cisco Modeling Labs (CML). Non sono redistribuibili liberamente. Se non hai accesso alle immagini Cisco, GNS3 supporta anche FRRouting (FRR) come alternativa open source per la parte di routing dei moduli 3 e 4.

Architettura GNS3 VM

GNS3 VM è una macchina virtuale basata su Ubuntu Server, distribuita in formato OVA per VMware Workstation / Fusion e VirtualBox. Gira in background sull’host e funge da server QEMU/KVM per i device del laboratorio. Il GUI GNS3 si collega a GNS3 VM via API REST su localhost, trasparentemente per l’utente.

Wireshark integrato

Wireshark è il principale analizzatore di protocollo open source e lo strumento di riferimento per tutto il percorso. GNS3 supporta la cattura del traffico su qualsiasi link della topologia facendo click destro sul link e selezionando Start capture. Internamente GNS3 usa tcpdump all’interno di GNS3 VM e passa i pacchetti in tempo reale a Wireshark sull’host tramite un pipe named. Questo meccanismo è fondamentale per tutto il percorso.

Step pratici di implementazione

Step 1 — Installazione GNS3 GUI e GNS3 VM

Obiettivo: avere GNS3 GUI avviato e connesso a GNS3 VM senza errori.

  1. Scarica il pacchetto GNS3 all-in-one installer (Windows/macOS/Linux) e GNS3 VM OVA dalla stessa versione del GUI.
  2. Importa l’OVA in VMware Workstation, VMware Fusion o VirtualBox. Assegna almeno 4 vCPU e 8 GB di RAM. Abilita nested virtualization (VT-x/AMD-V).
  3. Avvia GNS3 VM. Annota l’indirizzo IP mostrato a schermo.
  4. Avvia GNS3 GUI. Setup Wizard: scegli Run appliances on a remote server (GNS3 VM). Inserisci l’IP di GNS3 VM e porta 3080.
  5. Verifica: indicatore verde con scritta “GNS3 VM” in basso a destra nella GUI.
ControlloRisultato atteso
Indicatore server GUIVerde — GNS3 VM connessa
Servers SummaryGNS3 VM: Running

Step 2 — Import immagini Cisco IOSv e IOSvL2

Obiettivo: avere i template IOSv e IOSvL2 disponibili nella palette dispositivi di GNS3. Recupera i file .qcow2 tramite Cisco DevNet o Cisco CML.

  1. In GNS3 GUI: Edit → Preferences → QEMU → Qemu VMs → New.
  2. Nome template: Cisco-IOSv. RAM: 512 MB. vCPU: 1. Disco HDA: seleziona il file .qcow2 di IOSv.
  3. Ripeti per IOSvL2 con nome template Cisco-IOSvL2. RAM: 768 MB.

Verifica: trascina un’istanza IOSv sulla canvas, avviala e attendi il boot (~60 secondi). Console: deve comparire il prompt Router>.

Step 3 — Creazione progetto base e naming dei device

Obiettivo: creare il progetto GNS3 con naming standard e i primi 2 device nominati correttamente.

  1. File → New blank project. Nome: network-learning-path.
  2. Aggiungi un’istanza IOSv. Click destro → Change hostname: R1.
  3. Aggiungi una seconda istanza IOSv. Rinominala R2.
  4. Collega R1 Gi0/0 a R2 Gi0/0 con un link punto-punto.
  5. File → Save project.
  6. File → Export portable project → salva con naming canonico:
    module-00__shared__gns3__export-gns3__topology-bootstrap__v01.gns3project
    nella cartella gns3/exports/module-00/ del repo privato.
Naming device congelato

Non rinominare mai i device una volta assegnati. R1 e R2 saranno i router edge WAN nella topologia finale a 16 device.

Step 4 — Configurazione IP e prima capture Wireshark

Obiettivo: connettività IP tra R1 e R2 verificata con ping e capture ICMP salvata tramite Wireshark.

  1. Configura R1:
R1> enable
R1# configure terminal
R1(config)# interface GigabitEthernet0/0
R1(config-if)# ip address 10.0.0.1 255.255.255.252
R1(config-if)# no shutdown
R1(config-if)# end
R1# write memory
  1. Configura R2:
R2> enable
R2# configure terminal
R2(config)# interface GigabitEthernet0/0
R2(config-if)# ip address 10.0.0.2 255.255.255.252
R2(config-if)# no shutdown
R2(config-if)# end
R2# write memory
  1. Click destro sul link R1-R2 → Start capture. Wireshark si apre automaticamente.
  2. Da console R1: ping 10.0.0.2 repeat 5
  3. In Wireshark: verifica 5 Echo Request e 5 Echo Reply. Usa il filtro display icmp se necessario.
  4. Salva la capture con naming canonico:
    module-00__person-N__R1-R2__pcap__ICMP-Gi0-0__v01.pcap
    nella cartella evidence/participants/person-N/module-00/captures/.

Verifica: Success rate is 100 percent (5/5)

Analisi Wireshark

Punto di cattura: link tra R1 (Gi0/0) e R2 (Gi0/0). Riferimento: Wireshark User Guide.

Filtro display:

icmp

Pacchetti attesi: 5 ICMP Echo Request da 10.0.0.1 → 10.0.0.2 e 5 ICMP Echo Reply da 10.0.0.2 → 10.0.0.1.

Campi da osservare

  • Frame header: lunghezza del frame, interfaccia di cattura, timestamp.
  • Ethernet header: MAC sorgente e destinazione.
  • IP header: Source/Destination IP, TTL (valore iniziale 255 per IOS), Protocol (1 = ICMP). Riferimento: RFC 791 — Internet Protocol.
  • ICMP header: Type (8 = Echo Request, 0 = Echo Reply), Code (0), Identifier, Sequence Number. Riferimento: RFC 792 — ICMP.

Domande di analisi

  1. Qual è il TTL nei pacchetti inviati da R1? E in quelli inviati da R2? Perché il TTL di un router Cisco è 255 invece di 64 o 128?
  2. I numeri di sequenza ICMP sono incrementali? Di quanto?
  3. L’identificatore ICMP cambia tra i pacchetti di uno stesso ping?

Criterio di chiusura del modulo

Il Modulo 00 può essere dichiarato chiuso solo quando tutte le seguenti condizioni sono soddisfatte contemporaneamente:

  • GNS3 GUI avviata senza errori e connessa a GNS3 VM (indicatore verde).
  • Template Cisco-IOSv e Cisco-IOSvL2 visibili nella palette di GNS3.
  • Progetto network-learning-path salvato con R1 e R2 configurati.
  • Ping R1 → R2 con success rate 100% documentato nell’output CLI.
  • Capture Wireshark funzionante con almeno 10 pacchetti ICMP visibili.
  • Tutte le evidenze presenti nel repo privato con naming canonico corretto.
  • Checklist docs/verification/module-00-checklist.md completata e committata.
